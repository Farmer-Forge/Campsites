## What the review found

1. **V1's specs describe changes, not the finished app.** Each one is a change on top of the previous ones. Later specs override earlier ones, and some say nothing about the final state. For example, the 08-15 spec's campground detail route was removed by the 09-01 spec.
2. **V1's specs and code disagree in places, and the code is right.** The 08-15 spec promises a PWA, but V1 has no service worker. Five October changes shipped without a spec, and their plans were written afterwards:
   - admin stats and user management;
   - location retry and the search-location pin;
   - the road-trip redesign;
   - persistent location and the map pick;
   - Reserve and Directions links.

   **So V1.1's specs are written from V1's code, with V1's specs and plans as background.**
3. **Production's edge functions don't always match the repo.** On 2026-10-11, production was found running an older `ridb-sync`. `nps-sync` was never redeployed, so some rows still lack `state` in production (463 of the 4,900 rows have no `state`: 163 NPS, 243 USFS, 43 BLM and 8 USACE (counted from the seed, 2026-10-25)). The repo's `supabase/functions/` at `v1.0` is the contract. The production data, and so the seed, reflects what actually ran.
4. **V1 has no lint and no database tests.** Its checks are `ng build`, Vitest unit specs (dropped for V1.1), Deno tests for the `ridb-sync` and `nps-sync` transforms, and Prettier.
5. **MyGear's loop works, and its steps check themselves.** Each step in `task.md` has its own Verify instructions (`psql`, lint, build). Worker prompt rule 7 tells the worker to run them before ticking the box. What MyGear doesn't have yet is a second check run by the loop script itself after the worker says it's done: the "verification gate". It's designed in `myGear/docs/superpowers/specs/2026-10-11-loop-verification-gate-design.md` on the unmerged `loop-verification-gate` branch, with no code. (MyGear's checkout in WSL is currently on that branch.)
6. **MyGear's loop has React-specific parts** that need Angular versions:
   - worker prompt rule 8 (`.jsx`, `Design.MD`, `components/ui/*`);
   - `review.sh`'s dev server (Vite on 5173; Angular's is `ng serve` on 4200);
   - the worker image (Node 22; it needs Deno for the edge-function tests);
   - `seed-app.sql`, `seed-sample.sql` and `seed-dev.*`;
   - the parts of `create-new-project.md` that assume Forge's core plan and Tailwind.

   The rest is framework-neutral and copies over as is: `doloop.sh`, `chain.sh`, `loop-lib.sh`, the loop's own tests, resume after usage limits, and one PR per task.
7. **MyGear's `task.md` puts the code in the plan.** It's about 7,000 lines across 9 tasks, with exact code in each step. Campsites' `task.md` follows that pattern, so the specs must be detailed enough to write that code from.

**Inputs Phase 1 leaves for spec 2 (app shell) and the scaffold task:**
- **Local settings:** the app reads `src/environments/environment.local.ts` (gitignored; same shape as V1's `environment.ts`: `production`, `supabaseUrl`, `supabaseAnonKey`). `angular.json`'s `development` configuration swaps it in for `environment.ts` with `fileReplacements`. The committed `environment.ts` holds no keys. `review.sh` writes it in the canonical clone, but worker worktrees don't have it. So the scaffold task, and any step that runs `ng serve` or `ng test`, must write it from `$SUPABASE_URL`/`$SUPABASE_ANON_KEY` first.
- **Style files** named in worker prompt rule 8: `docs/superpowers/Design.md`, `docs/superpowers/style-task.md`, and shared components in `src/app/shared/ui/`.
- **Ports:** the review app holds 4200 on Ralph, so a worker step that serves the app needs another port (e.g. 4201).
- **Deno pins:** `deno.lock` is probably not read without a `deno.json`, so steps should run `deno test --lock=deno.lock --frozen supabase/functions`.
